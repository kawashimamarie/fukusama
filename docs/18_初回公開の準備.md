## 1. FTP アカウントをサイト別のフォルダに限定できるか

| 項目 | 確認結果 |
|---|---|
| できるか | **できる（と判断）**。RS プランのコントロールパネル「ファイル管理」で、ドメインを切り替えて FTP アカウントを追加するときに「接続先ディレクトリ」を指定する（[手順の解説記事](https://pcmous.blog/web-relation/onamae-com-sd-rs-ftp-acount/)。公式ヘルプの SD プランの記事も「ディレクトリを指定して権限を与えられる」［[ヘルプ](https://help.onamae.com/answer/9070)・本文は自動取得が拒否され未読］） |
| 実績 | Nexus が同じお名前.com RS で、接続先を `public_html/ne-xus.co.jp` に限定したアカウントで公開済み。「外へ出られないか」（`..`・`/..`・`/public_html`・`~`・絶対パス）の確認に合格している |
| 初回の確認のみで分かること | Summary の「上位・他サイトへのアクセス」に、7つの試行（`..`・`../..`・`/..`・`/`・`/public_html`・`~`・`~/public_html`）と任意の絶対パスの結果が「拒否」「ルートと同じ」で並ぶこと。「外が見える」が1つでもあれば、その時点で止まり、何も保存・書き込みしない |
| この仕組みでの確かめ方 | 「確認のみ」の最初に、毎回これを確かめ、1つでも外れれば何もしない：ログイン直後が `/`・一覧にほかのドメインのフォルダや `public_html` がない・`..`／`../..`／`/..`／`/`／`/public_html`／`~`／`~/public_html`（＋任意の Secret `FTPS_<サイト>_PARENT_ABS` の絶対パス）が拒否されるかルートと同じ・サイトの目印がある・FTPS と公開URLの中身が同じ |

**限定できなかった場合の代わり（推奨順）**
1. **そのサイトは自動公開しない**：メインの FTP アカウント（全ドメインに届く）を GitHub に置かない。docs/15 の手作業（ファイルマネージャー）で公開する
2. お名前.com のサポートに、ドメイン別のアカウントの作り方を問い合わせる
3. （行わない）全ドメインに届くアカウントで「サブフォルダだけに書く」ようにする方式は、パスワードが漏れたときに Nexus を含む全サイトに届くため採らない。仕組みも、ほかのドメインのフォルダが見えた時点で止まる

## 2. fukushin-deploy の安全な設定

GitHub の個人アカウントの無料プラン（Free）では、**非公開リポジトリのブランチ保護・ルールセットは使えない**（[GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)：ブランチ保護は Free では公開リポジトリだけ）。そのため、次の組み合わせで守る。

| 守り | 内容 | 設定・確認する場所 |
|---|---|---|
| 書き込める人 | ご本人だけ（共同作業者なし） | Settings → Collaborators |
| Claude Code が届かない | Claude の GitHub App の対象に入れない | GitHub の Settings → Applications → Installed GitHub Apps → Claude → Configure →「Only select repositories」で fukushin-deploy が一覧にないこと |
| Actions のトークン | 既定は読み取りのみ・プルリクエストの作成と承認は不可 | Settings → Actions → General →「Workflow permissions」＝Read repository contents and packages permissions、「Allow GitHub Actions to create and approve pull requests」＝オフ |
| 使ってよい Actions | GitHub 公式（`actions/checkout`・`actions/upload-artifact`・`actions/download-artifact`）だけ。すべてコミット SHA で固定済み。「Allow actions created by GitHub」（`actions`・`github` の組織）の範囲内で、「Require actions to be pinned to a full-length commit SHA」もオンにできる。ワークフローはジョブごとに必要な権限（記録の書き込み・別の実行のバックアップの読み取り）を `permissions` で指定しているため、既定を「読み取りのみ」にしても動く（[GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)） | Settings → Actions → General →「Allow …, and select … actions」→「Allow actions created by GitHub」だけをオン |
| ワークフローの変更 | **GITHUB_TOKEN ではワークフローを変更できない**（[権限の一覧](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) に workflows がない）。公開の処理（deployer/）のハッシュをワークフローに固定し、deployer/ だけを書き換えても動かない（照合で止まる。改ざんの模擬で確認済み） | ― |
| Secrets の渡し方 | FTPS 情報は「確認」「公開」「復元」のステップにだけ、対象のサイトの分だけ渡す。ビルド（fukusama のコード）のジョブには渡さない | ― |
| 手動実行できる人 | 書き込み権限のある人だけ（＝ご本人だけ） | ― |
| 通知 | 公開の失敗をメールで受け取る | GitHub の Settings → Notifications → System → Actions →「Only notify for failed workflows」 |
| 2段階認証 | ご本人のアカウントが乗っ取られると防げない | GitHub の Settings → Password and authentication |

仕組みを更新するとき（まれ）：fukusama の `deploy-repo/` の中身（変更されたファイル）を、ご本人がアップロードし直す。Claude Code は変更点（特に安全に関わるもの）を必ず説明する。

## 3. バックアップの保存先・保存期間・復元できること

| 層 | 何を | 保存先 | 期間 | 復元のしかた |
|---|---|---|---|---|
| 1. 公開ごとの事前バックアップ | 上書きするファイルの公開前の中身・福記美食の元の .htaccess・計画（追加するファイルの一覧とハッシュ） | fukushin-deploy の Actions の成果物 `backup-<サイト>-<実行番号>` | 90日（非公開リポジトリは Settings → Actions → General で最大 400日まで延長可） | 自動（検証に不合格なら同じ実行で）／手動の「復元」ワークフロー |
| 2. お名前.com の自動バックアップ | Web・メール・データベースの全体 | お名前.com のサーバー | 14日（毎日） | コントロールパネル「サーバー」→「自動バックアップ」→ 日付の「復元」。**Web データは別のフォルダに復元される**（場所は「復元履歴」）ので、そこから必要なファイルを戻す（[公式ガイド](https://www.onamae-server.com/guide/rs/p/63)） |
| 3. 手元の控え | 福記美食の公開中ページの HTML・画像（PHP・データベースなし） | fukusama の `fukuki-site/live-backup-20261010/` | 無期限 | 参照用 |

**公開の前に確かめること**：「確認のみ」でも、事前バックアップを保存 → 取り出し → SHA-256 で照合する（Summary に「バックアップの保存と取り出しの確認：合格」）。初回公開の前に、3サイトの確認のみでこれが合格していること。
**復元できることの確かめ方**：層1は、毎回「保存 → 保存先から取り出し直し → ハッシュで照合」した取り出し済みのバックアップを公開に使う。手動の復元は `mode=verify` で、本番に接続せずにいつでも照合できる。模擬テストと本物の Apache で、復元後のフォルダが公開前と**完全に一致**することを確認済み。
**容量の見込み**（無料プランの非公開リポジトリの保存容量 500MB は Nexus と共有・月ごとには戻らない。超えると新しい成果物を保存できなくなり、その場合は公開前のバックアップの保存で止まる＝書き込まない側）

| 成果物 | 1回あたり | 保存期間 | 見込み |
|---|---|---|---|
| 事前バックアップ（初回） | ebisenka.jp 約10KB（計画だけ）・福記美食 約10KB（計画＋元の .htaccess）・コーポレート 約90KB（上書きする5ファイル 77KB＋計画） | 90日 | 合計 約0.1MB |
| 事前バックアップ（通常更新） | 変わるページ 1〜3枚＋計画で 20〜80KB。画像の差し替えで 〜0.3MB。最大はコーポレートの大きな PNG（2.4MB） | 90日 | 3サイト×月20回でも 90日で 約10MB（画像の多い月でも 100MB 未満） |
| 確認のみのバックアップ | 上と同じ大きさ | 14日 | ごくわずか |
| ビルド | 約14MB（3サイト分・コーポレートが 11.6MB） | 1日 | 新しいコミットのある日に最大で数十MB（翌日に消える） |
| 結果の記録 | 数KB | 90日 | ごくわずか |

使用量は GitHub の Settings → Billing and plans → Usage で確認できる（Nexus 分を含む）。
**初回だけ追加でお願いすること**：福記美食の切り替えの前に、ファイルマネージャーでフォルダ全体（特に `.htaccess`・`wp-content`）をダウンロードして手元に保管（層2の14日を過ぎても戻せるように）。

## 5. 福記美食の切り替え（WordPress → 静的サイト）

**確認のみ（A）で確かめること**
- 接続先：WordPress の目印・FTPS と公開URLの中身が一致
- 新しいページと同じ名前のファイル・フォルダが既にないこと（あれば「置き換え」として一覧に出る → 中身を確認してから判断）
- `.htaccess`：キャッシュのプラグイン（WP Super Cache・W3 Total Cache・LiteSpeed Cache・WP Rocket など）の設定があれば**止まる**（古いトップが表示され続けるため。プラグインを停止して設定を外してから）。公開中のページの HTML からは、WordPress 7.1.3・All in One SEO・Site Kit のみが確認でき、キャッシュのプラグインの痕跡はなかった
- サーバーキャッシュ（nginx）が有効（`x-nginx-cache`）。検証はキャッシュを通さずに行う。古いトップが残れば警告 → コントロールパネルの「キャッシュの削除」

**公開（B）の順番**（自動）：フォルダ → 画像・CSS → 各ページ →（.htaccess の先頭に転送設定）→ **最後にトップページ**。WordPress のファイル・データベース・`wp-content/uploads` には触れない

**公開後に実サーバーで確かめること**
- [ ] https://ebisenka-seavans.com/ が新しいトップ（「お弁当は、店頭でお買い求めいただけます。」の案内）
- [ ] /bento/・/kitchen/・/wholesale/・/access/・/contact/ が表示される
- [ ] 旧URL：/lunch/・/food/ → /bento/、/commitment/ → /kitchen/、/info/ → /access/、/party/ など → トップ（301）
- [ ] /wp-admin/ にログインできる（WordPress は残っている）
- [ ] 以前の画像のURL（/wp-content/uploads/…）が今までどおり開ける（Google ビジネスプロフィールなどから参照されている可能性）
- [ ] スマートフォンでの表示・サーバーキャッシュの削除

**元に戻す（どの段階でも、WordPress の状態に完全に戻る）**
1. 自動：公開後の検証に不合格なら、同じ実行で戻る（追加したファイルの削除・.htaccess を元に）
2. 手動：Actions →「復元（福進発展3サイト）」→ site＝fukuki・run_id＝公開の実行番号・mode＝verify → 問題なければ mode＝restore・confirm＝`ebisenka-seavans.com`
3. 仕組みが使えないとき：ファイルマネージャーで `index.html` を削除（＝トップが WordPress に戻る）→ 保管した元の `.htaccess` で上書き → サーバーキャッシュを削除。必要なら追加したフォルダ（bento・kitchen・wholesale・access・contact・assets）も削除
4. それでも戻らないとき：お名前.com の自動バックアップ（14日）から Web データを復元し、元のファイルを戻す
WordPress の削除は、切り替えが安定し、復旧が不要と判断できた後に、別途ご承認のうえで行う。
