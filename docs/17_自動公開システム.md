# 17 自動公開システム（GitHub Actions・FTPS）（2026-10-12）

福進発展グループの3サイトを、**Claude Code の修正 → 自動テスト → GitHub（main）→ 公開前バックアップ → FTPS で公開 → 公開後の検証 → 異常時の自動復元 → 結果の記録** まで自動で行う仕組み。
**現在の状態：実装・ローカルでの模擬テストまで完了。本番サーバーへの書き込みは一度も行っていない。** 初回公開はご本人の明示的な承認（手動実行）が必要。

初回公開の準備（FTP アカウント・リポジトリの設定・バックアップ・手順・福記美食の切り替え・Secrets の登録）は `18_初回公開の準備.md`。

## 1. 全体の構成

```
fukusama（公開リポジトリ・Claude Code が作業）            fukushin-deploy（非公開・ご本人だけ・新規作成）
  サイトのソース・ビルド・品質確認（site-ci）                  本番の FTPS 情報（Secrets）はここだけ
  deploy-repo/ ＝ fukushin-deploy に置く中身の原本     ──▶    .github/workflows/deploy.yml・restore.yml
                                                              deployer/（公開の処理。毎回 SHA-256 を照合）
        main の最新（CI 合格）  ◀────── 読むだけ（公開リポジトリのためトークン不要）
```

| 段階 | どこで | 内容 | 本番への書き込み |
|---|---|---|---|
| 1. 修正・テスト | fukusama（Claude Code） | 修正 → site-ci（ビルド・検査・フォーム・表示・公開の仕組みのテスト） | なし |
| 2. 反映 | fukusama の main | CI 合格のコミットを main へ | なし |
| 3. 変更の検出 | fukushin-deploy（毎時・日本時間 8:05〜21:05） | main の最新・CI 合格・未処理のサイトを決める | なし |
| 4. ビルド | 同（秘密情報なしのジョブ） | fukusama のそのコミットから3サイトを作り直す | なし |
| 5. 確認・計画・事前バックアップ | 同（サイトごと・読み取り専用の接続） | 接続先の確認 → 差分 → 上書きするファイルを取得 → 保存 → 保存先から取り出し直して照合 | なし |
| 6. 公開 | 同（サイトごと） | 書き込み直前の再確認 → 確認用ファイルで接続先を確認 → 一時ファイル＋名前の変更で1件ずつ | **あり** |
| 7. 公開後の検証 | 同 | 公開URL（キャッシュを通さない）で中身・ページ・参照・転送・見えてはいけないURL・フォームの非送信テスト | なし |
| 8. 異常時 | 同 | 不合格 → この実行の事前バックアップで自動で元に戻し、もう一度確認。戻せなければ【至急】で停止 | あり（復元） |
| 9. 記録 | 同 | `deploy-state` ブランチに結果、（任意）fukusama のコミットに結果の状態 | なし |

### 採用した理由（Nexus との比較）
| 項目 | Nexus | 福進発展3サイト | 理由 |
|---|---|---|---|
| 秘密情報の置き場所 | 専用の非公開リポジトリ（nexus-deploy） | 同じ考え方で **fukushin-deploy**（Nexus とは別） | Claude Code がアクセスできるリポジトリに置くと、取り出せてしまうため（Nexus の検討結果をそのまま採用） |
| 公開の起動 | 公開依頼ファイル → 受付 → 公開許可のイシュー → 承認／自動公開 | **main の最新（CI 合格）を毎時確認し、変わったサイトだけ公開** | イシュー・承認コメント・公開依頼をなくし、通常更新を全自動にするため（ご希望） |
| 承認 | イシューへの「承認」コメント（60分・一度限り） | **初回・切り替え・安全に関わる変更だけ**、ご本人が Actions の手動実行（確認入力＝ドメイン名） | Claude Code は fukushin-deploy を操作できないので、手動実行そのものが偽造できない承認になる |
| 自動公開の範囲 | コードの定数 AUTO_PUBLISH | 変数 **AUTO_PUBLISH_SITES**（サイトごと） | ご本人だけが変えられ、サイトごとに有効化できる |
| 公開できるファイル | 固定の14ページ＋決まった形の画像だけ | **ビルドに含まれるファイル**（種類・場所を制限）。差分だけを書き込む | 3サイトは静的サイトで、CSS・画像の更新も通常更新に含めるため |
| 削除 | しない | **しない**（元に戻すときに、その実行で追加したファイルだけを削除） | 同じ |
| 実装 | Node.js＋curl・ワークフローにコードを埋め込み（最大 373KB） | **Python 標準ライブラリだけ**（約1,200行）・deployer/ を SHA-256 で照合 | 保守しやすさ。fukusama のビルドも Python |
| 更新の手順 | 更新専用の GitHub App＋イシューで承認 | ご本人が deployer/・workflows を貼り替え（まれ） | 仕組みの変更は「承認が必要な変更」のため、手で行う形で十分 |

## 2. 3サイトの管理
- ソースは1つのリポジトリ（fukusama）で、フォルダで分ける：`bento-site/`（ebisenka.jp）・`fukuki-site/`（ebisenka-seavans.com。共通の CSS・JS は bento-site のものを使用）・`corporate/`（fukushin-e.co.jp）
- 公開成果物は `python3 scripts/build_sites.py` で毎回作り直す（**旧 ZIP の手動管理は不要**）。同じコミットからは同じバイト列になる（日付は各サイトを最後に変えたコミットの日付）。2026-10-10 13:49 の公開用 ZIP と完全に一致することを確認済み。コーポレートの39ファイルのうち、公開中と違うのは承認済みの6ファイルだけ（公開URLとハッシュで照合）
- 変わったサイトの判定は「ビルドとサーバーの中身の比較」で行う。共通の CSS を変えれば福記美食・弁当事業の両方が、コーポレートだけを変えればコーポレートだけが公開対象になる
- 公開・バックアップ・復元・記録・同時実行の制御（`concurrency: deploy-<サイト>`）はサイトごとに独立。1サイトの失敗で他のサイトは止まらず、巻き戻らない

**必ず止まる（承認しても公開しない）もの**：書き込まないファイルがビルドに含まれる・許可していない種類のファイル・接続先の目印が違う・ほかのドメインのフォルダが見える（アカウントの範囲が広すぎる）・FTPS と公開URLの中身が違う・サーバー証明書を検証できない（パスワードを送る前に止まる）・前回の一時ファイルが残っている・計画の後にサーバーが変わった・main が進んだ（古い実行で新しい内容を上書きしない）。

## 5. ご本人に行っていただく準備（初回だけ）
1. **FTP アカウントを3つ追加**（お名前.com のコントロールパネル →「ファイル管理」→ FTP アカウントの追加）：接続先ディレクトリをそれぞれ `public_html/ebisenka.jp`・`public_html/ebisenka-seavans.com`・`public_html/fukushin-e.co.jp` に限定。パスワードは新しいランダムな文字列。Nexus のアカウントは流用しない
2. **GitHub で非公開リポジトリ `kawashimamarie/fukushin-deploy` を作成**（Private・README あり）
3. **Claude の GitHub App の対象に入れない**：GitHub → Settings → Applications → Installed GitHub Apps → Claude → Configure が「Only select repositories」で、fukushin-deploy が一覧にないこと（Nexus の nexus-deploy と同じ）
4. fukushin-deploy の **Settings → Actions → General**：Workflow permissions＝「Read repository contents and packages permissions」、「Allow GitHub Actions to create and approve pull requests」＝オフ。Settings → Notifications で Actions の失敗の通知（メール）を有効に
5. **fukusama の `deploy-repo/` の中身を fukushin-deploy に置く**：`.github/workflows/deploy.yml`・`.github/workflows/restore.yml`・`deployer/`（9ファイル。`SHA256SUMS` を含む）。「Add file → Upload files」でフォルダごと
6. **Secrets を登録**（Settings → Secrets and variables → Actions → New repository secret。値はチャット・Issue・PR に書かない）

| Secret | 内容 |
|---|---|
| `FTPS_EBISENKA_HOST`・`FTPS_EBISENKA_USER`・`FTPS_EBISENKA_PASSWORD` | ebisenka.jp 用の FTP アカウント |
| `FTPS_FUKUKI_HOST`・`FTPS_FUKUKI_USER`・`FTPS_FUKUKI_PASSWORD` | ebisenka-seavans.com 用 |
| `FTPS_CORPORATE_HOST`・`FTPS_CORPORATE_USER`・`FTPS_CORPORATE_PASSWORD` | fukushin-e.co.jp 用 |
| `FUKUSHIN_STATUS_TOKEN`（任意・推奨） | fine-grained personal access token：対象 **fukusama だけ**・権限 **Commit statuses: Read and write だけ**・期限つき。公開の結果を fukusama のコミットに書き、Claude Code が結果を読めるようにする |

HOST は、お名前.com のコントロールパネルに表示される FTP ホスト名（サーバー証明書のホスト名と一致する名前。Nexus で使っているものと同じ形式）。**2026/10/21 のサーバーメンテナンスの対象の場合、10/22 以降は新しいホスト名に更新する。**

7. **Variables**：`AUTO_PUBLISH_SITES` を作成し、**最初は空**（自動公開しない）

## 6. 初回公開（ご本人の承認・サイトごとに）
順番：**ebisenka.jp → 福記美食 → コーポレート**。各サイトで：
1. fukusama の main に最新の内容が入っていることを確認（この作業ブランチ `claude/bento-business-site` のマージ。§9）
2. fukushin-deploy の Actions →「公開（福進発展3サイト）」→ Run workflow：site＝対象・**mode＝check**（読み取りのみ）
3. Summary で、接続先の確認・追加／置き換えの一覧・承認が必要な理由を確認（Claude Code にスクリーンショットを共有いただければ照合します）
4. もう一度 Run workflow：**mode＝publish・confirm＝ドメイン名**（例 `ebisenka.jp`）
5. Summary の「公開しました」と検証結果を確認。キャッシュの注意が出たら、コントロールパネルで「キャッシュの削除」
6. ebisenka.jp は、フォームの**実送信テスト**と**返信テスト**（docs/15 の手順）。終わるまで「実際の受信は未確認」
7. 福記美食は、/wp-admin/ にログインできること・旧URLの転送を確認（WordPress は削除しない。§8）

コーポレートの初回で書き込むのは、承認済みの6ファイル（index・business・restaurant・contact・style.css・福記美食のロゴ）だけ。mail.php・.htaccess には触れない。

## 7. 通常更新（全自動）への切り替え
3サイトの初回公開が問題なく終わったら、ご本人が fukushin-deploy の Variables `AUTO_PUBLISH_SITES` を `ebisenka,fukuki,corporate` にする（一部のサイトだけでもよい）。
以後は、Claude Code に修正を依頼 → Claude Code が修正・テストし、CI 合格を確かめて main に反映 → **次の毎時の確認（日本時間 8:05〜21:05）で自動公開** → 結果は fukusama のコミットの状態（`fukushin-deploy/<サイト>`）と公開URLで Claude Code が確かめて報告、の流れになる。ご本人の操作は不要。
- 急ぐとき：Run workflow（mode＝auto）で、すぐに同じ判定で公開
- 承認が必要な変更（§3）は自動では公開されず「承認待ち（awaiting-approval）」になる → mode＝publish・confirm で公開
- 自動公開を止める：`AUTO_PUBLISH_SITES` から外す（またはワークフローを Disable）。**定期の確認は `AUTO_PUBLISH_SITES` に入っているサイトだけを処理し、空のときはサーバーに接続しない**（初回公開までは、ご本人の手動実行だけが接続する）

## 8. 元に戻す・異常時
- **自動**：公開後の検証に不合格・途中の失敗 → その実行の事前バックアップで公開前の状態に戻し、FTPS と公開URLで確認（Summary に「元に戻しました」）
- **手動の復元**：Actions →「復元（福進発展3サイト）」→ site・run_id（戻したい公開の実行番号）・mode＝verify（本番に接続せず照合）→ mode＝restore・confirm＝ドメイン名。その後に別の公開があれば止まる（新しいものから戻す）。復元すると、そのサイトの自動公開は止まり、次は承認が必要
- **【至急】（自動の復元も失敗）**：それ以上は自動で書き込まない。Summary の「戻せなかったもの」を確認 → 手動の復元 → それも失敗したら、Actions の成果物 `backup-<サイト>-<実行番号>` をダウンロードし、`files/` の中身をファイルマネージャーで同じ場所に上書き（福記美食は `htaccess.orig` を `.htaccess` に）。その実行で追加したファイル（Summary の「追加」）は削除してよい
- バックアップの保存期間は90日（最大400日まで延長可）。お名前.com の自動バックアップ（14日・別フォルダに復元）も併用。詳細は `18_初回公開の準備.md` §3
- **福記美食の WordPress**：切り替え後も削除しない（ファイル・データベースとも残る）。正常動作を確認し、復旧が不要と判断できた後に、別途ご承認のうえで整理する

## 10. 残るリスク
1. FTP アカウントのパスワードが漏れた場合、そのサイトのフォルダ全体に届く（コードでは保護対象に書かないが、アカウント自体は制限できない）→ fukushin-deploy にだけ置く・漏えいが疑われたらお名前.com でアカウントを削除
2. Claude の GitHub App の対象に fukushin-deploy を入れると境界が崩れる（「All repositories」にしない）
3. 自動公開の確認は毎時（GitHub の定期実行は混雑で遅れることがある）。非公開リポジトリの Actions の無料枠（月2,000分・Nexus と共有）のうち、毎時の確認で月約420分＋公開1回あたり数分
4. 公開後の検証は公開URLの中身・状態・参照まで。表示の崩れ（見た目）は fukusama の CI の表示確認で、公開前に確かめる
5. 書き込み直前の再確認から書き込みまでの数秒の間に、ほかの人がファイルマネージャーで同じファイルを変えた場合は検出できない（公開中は手作業をしない）
6. サーバーキャッシュ（nginx）に古いページが残ることがある。検証はキャッシュを通さずに行い、残っていれば警告（コントロールパネルの「キャッシュの削除」）
7. 公開の仕組みの更新（deployer/・ワークフロー）は、ご本人が貼り替える。毎回の実行の最初に SHA-256 で照合し、貼り間違い・欠けは止まる
